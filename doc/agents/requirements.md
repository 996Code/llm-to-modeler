# 交付要求（硬标准——不满足不算完成）

## 代码交付要求

| # | 要求 | 验证方式 |
|---|---|---|
| 1 | 全量 pytest 绿（~1871 例） | `cd backend && .venv/bin/python -m pytest tests/ -q` |
| 2 | 新功能/修复配新用例：主路径 + 边界 | 用例文件随代码同提交 |
| 3 | 前端改动类型检查过 | `cd frontend && npx vue-tsc --noEmit` |
| 4 | 批量改动即改即测（先读签名/调用方） | 改完该文件测试立即跑，不等最后 |
| 5 | 不引入新依赖除非必要；依赖变更需说明 | requirements.txt diff 审查 |

## 验证要求

- **真实环境验证**：兼容性/行为论断走真实调用路径（真实库、真实上游），不用假对象下结论。
- **UI 必须浏览器实测**：chrome-devtools MCP 真点真输，验证黄金路径 + 边界；只跑类型检查不算 UI 验证。
- **部署后冒烟**：上服务器后跑核心链路（如 KG：上传→导入触发→检索问答），启动日志零 error 才算上线完成。
- **agent 产物核实**：后台 agent 汇报完成前，核实文件真实存在、内容真实落地。

## 提交与发布要求

- commit message 讲 **why** 优先于 what，中文，与仓库风格一致。
- **双远程推送**：GitHub（origin）+ 内网 GitLab（njmind）一起推。
- **修复双落**：feat/bid-demo 与 main 都要有（cherry-pick），保持两分支同步。
- 部署从**干净 worktree 出包**，不带主工作区在途文件。

## 汇报要求

- 结论带证据（命令输出/查询结果/截图），不凭记忆断言。
- 覆盖面如实报告：全量过 ≠ 审过，没测到的部分明说。
- 用户质疑交付状态：先跑真实验证拿证据再回答。

## 文档与感知面要求

- 新能力落地同步三处：任务日志、页面文案、错误信息——用户看不见 = 没上。
- 文档只描述当前行为，不写历史叙事（"从 X 改成 Y"）。
- 对外地址一律 `/ai-modeler/api/...` 网关形式。

## 明确不做的事

- 不为不存在的场景加防护（Docker 内网 + admin 门控已护住的风险不叠闸）。
- 不静默降级：交互链路 LLM 失败直接报错。
- 不动别人的部署（28080 红线）；共享宿主机不加内存、不压负载。
- 不碰用户在途未提交文件（主工作区的 WIP 归用户）。
