## 一、三分钟理解整个系统

一句话：**这是一个"自然语言 → 结构化制品"的平台，表单只是它的第一个插件**。

一个用户请求的完整旅程（以"把姓名字段改成必填"为例）：

```
用户在对话框输入 ──→ POST /api/config/chat（SSE 流式）
                        │
                        ▼
                 ┌─ 引擎（领域无关）─────────────┐
                 │ classify：LLM 从注册表挑工具    │ ← 工具清单由插件注册，
                 │   选中 modify_form（表单插件）  │   引擎不认识任何表单词
                 └──────────┬───────────────────┘
                            ▼
                 ┌─ 插件 njmind_form ────────────┐
                 │ fetch_guide → 规划指令(LLM)    │ ← 增量协议：LLM 只输出
                 │   → 确定性合并 → 差分校验       │   "指令"不重写整个配置
                 └──────────┬───────────────────┘
                            ▼
                 SSE 实时推送每个阶段 → 前端进度条（获取指南/规划指令/应用修改/校验结果）
                            ▼
                 result 事件：新配置 → 消息流里出现「配置卡片」
                            ▼
                 用户点「应用」→ APPLY 协议 → 宿主画布渲染（不落库！）
```

两条铁律贯穿所有设计：

1. **引擎/前端只保留机制，领域内容全部住插件**（config.yaml 声明 + prompts/ + tools/）；
2. **AI 永不落库**——保存只属于业务人员手动的保存按钮，AI 产物最多渲染到画布。

## 二、插件（pack）开发：从零写一个"请假申请"插件

### 2.1 一个 pack 长什么样

```
backend/src/domains/leave_application/     ← 目录名即插件名，自动发现
├── pack.py                ← 入口：注册工具（必须提供 create_registry）
├── config.yaml            ← manifest：插件向平台声明一切（见第三节）
├── prompts/               ← 本插件的 prompt 模板（j2）
│   └── parse.j2
└── tools/
    └── submit_leave.py    ← 工具实现（Tool 或 CompositeTool 子类）
```

系统启动时 `domains/__init__.py` 扫描所有子目录并 import `pack.py`——新 pack **默认启用、即插即用**。启用/禁用是一套持久化状态机（`services/pack_state.py`，落盘 `data/pack_state.json`，env `PACKS_ENABLED` 可覆盖）：管理端插件中心可随时启停并**热装配**（`api/admin.py` 的 toggle 接口，装配失败自动回滚旧运行态），无需重启后端。

### 2.2 写工具（以请假为例）

```python
# tools/submit_leave.py
from sdk.tool import CompositeTool, ToolResult, ToolContext, ClarificationRaised

class SubmitLeaveTool(CompositeTool):
    name = "submit_leave"                       # LLM 看到的工具名（全局唯一）
    description = "提交请假申请"
    when = "用户想请假、销假、查审批状态"          # 引擎用它拼意图识别 prompt

    steps = ["parse_info", "submit"]            # 管线步骤（每步一个 _step_xxx 方法）
    pipeline_steps = [                          # 前端进度条节点（动态下发）
        {"key": "parse_info", "label": "解析申请"},
        {"key": "submit", "label": "提交"},
    ]

    def _step_parse_info(self, state, ctx):
        ctx.emit("stage", "parse_info", "正在解析您的请假需求...")
        # ... 调 LLM 解析 → 信息不足时 raise ClarificationRaised([...问题])
        #     追问会被引擎转成 interrupt，前端渲染追问卡片，用户回答后从断点继续

    def _step_submit(self, state, ctx):
        # ... 校验并产出结果
        return ToolResult(
            artifact=application,         # 制品（结构化结果）
            artifact_type="data",         # 'data'=数据制品 / 'config'=配置制品
            summary="已生成请假申请（3 天年假，12/24 起）",
        )
```

注册：

```python
# pack.py
def create_registry():
    r = ToolRegistry()
    r.register(SubmitLeaveTool())
    return r
```

**上线即生效**（新 pack 默认启用；管理端启停走热装配，同样无需重启）：意图识别 prompt 自动把 `submit_leave` 纳入候选（引擎从注册表
动态生成，无硬编码），前端进度条自动显示"解析申请/提交"两个节点。

**链路打点（可选但强烈建议）**：工具内部的关键步骤可以写入会话链路，在管理端
（`/ai-modeler/admin.html` → 会话 → 查看）的时间线上与引擎自动打点（意图路由、
工具执行耗时、历史压缩）汇成同一条链路：

```python
def _step_submit(self, state, ctx):
    started = time.time()
    ok = upstream.submit(...)          # 调上游
    ctx.trace(                          # ← 业务打点入链（Fail-Open，写失败不影响主流程）
        "submit_leave.upstream",        #   stage：建议 "工具名.动作" 命名空间
        title="提交上游",
        status="ok" if ok else "error",
        duration_ms=int((time.time() - started) * 1000),
        detail={"code": application.code},   # 小体积结构化明细
    )
```

引擎自动入链的环节（无需 pack 做任何事）：意图路由决策（两级路由选了哪个
pack/工具、是否兜底）、工具执行耗时与结论（ok/ask/error）、LLM 与上游每次
调用的请求/响应/耗时（`call_logs` 表）、历史压缩。LLM 调用的环节标签
（`stage`）由引擎与各工具自动标注（`route_pack`/`create_form.generate` 等），
pack 内部调 `ctx.llm_client.chat_json(..., stage="your.step")` 可自定义。

**底层全封装契约（插件开发的铁律）**：插件的一切底层调用必须走 `ctx` 提供的
通道，**禁止直接 import openai / requests / httpx 直连外部服务**——

| 插件要做什么 | 唯一合法通道 | 平台自动获得 |
|-------------|-------------|--------------|
| 调 LLM | `ctx.llm_client.chat / chat_json` | 完整 prompt/响应/耗时/token 入 `call_logs`，关联会话 |
| 调上游业务 API | `ctx.asset_client.*` | 请求/响应/状态码/耗时入 `call_logs`，会话归属由线程上下文自动绑定（插件不用传 conv_id） |
| 调图/向量库等自有设施 | `sdk.observability.log_pack_call(...)`（call_type 用同模块常量 graph/vector/fulltext;conv_id/pack 自动解析） | 与 llm/upstream 同表同视图,管理端四类筛选+召回摘要（参考 `knowledge_graph/retrieval.py` 的 `_log_retrieval_call`——已委托该 helper） |
| 要 PG 表（关系型存储） | `sdk.relational_store.PackRelationalDB("<pack名>")` | pack 独立 PG schema（物理隔离）+ 共享平台连接池 + 事务/占位符同规；禁止插件直连 psycopg 或 import 平台 services 层（参考 `knowledge_graph/store.py`） |
| 写业务打点 | `ctx.trace(...)` | events 表 kind=trace，进管理端链路时间线 |
| 推前端进度 | `ctx.emit(...)` | SSE 实时事件 |

这样"链路可观测"是平台能力而不是插件自觉：只要走 ctx，监控链路就是全的；
插件作者只需要关心自身业务逻辑。LLM 完整 prompt 入库由 `LLM_LOG_FULL`
控制（默认开，图片以占位符记录防体积爆炸）。

### 2.3 制品的两种通道（决定了前端渲染与交互）

| | `artifact_type="config"` | `artifact_type="data"` |
|---|---|---|
| 语义 | 可应用的配置（表单/报表布局…） | 数据结果（申请单、查询结果…） |
| 前端渲染 | **配置卡片**（字段统计+动作按钮组） | **数据卡片**（key→中文标签平铺） |
| 动作 | 按 manifest `actions` 声明（见 3.2） | 无（纯展示） |
| 举例 | "把姓名改成必填"→ 新表单配置 | "帮我请 3 天假"→ 申请单结果 |

请假插件产出 data 制品 → 数据卡片 → 天然没有"应用/回滚"按钮，互不打扰。

### 2.4 可选钩子：create_router()（pack 二级路由）

引擎一级路由选中领域后，由 pack 自己的二级路由在本 pack 工具集内挑具体
工具。`pack.py` 可选提供 `create_router()`（`domains/__init__.py:204-209`），
缺失时回退 `DefaultPackRouter`（中性框架，行为同旧扁平路由）：

- `route(user_input, artifact, history, llm_client, conv_id)` 返回
  `(tool_name, confidence)` 元组（`sdk/pack_router.py:88-131`）——tool_name
  为 None 表示无匹配，confidence 是 LLM 自评确信度（0-1，无 LLM 的降级
  路径给 1.0）；`conv_id` 可选，透传给 LLM 调用日志（管理端链路按会话关联）；
- 引擎按签名协商兼容旧实现（只返回字符串的旧 pack 按 confidence=None
  处理；route 没有 conv_id 参数时不硬传，见 `engine/nodes.py:185-204`）——
  pack 未跟进协议升级也不会崩；
- 领域规则示例见 `domains/njmind_form/router.py`：LLM 语义主判 + 数据铁律
  复核（画布为空时 modify 不进候选）+ `[script:js]`/`[script:sql]` 消息标记
  确定性分流（代码直选工具，零 LLM 调用）。
- **一级路由的 packs 子集声明（pack 无关,你的插件零感知）**：宿主/前端可在
  chat 请求带 `packs: ["njmind_form", ...]` 声明插件链路子集——引擎一级
  路由只在子集内路由（"谁发起请求谁声明插件"）：子集只剩 1 个 pack 时直通
  （零 LLM）,多个时 LLM 候选收窄,未声明则全量语义路由。**pack 自身不用改
  任何代码**（`engine/nodes.py:761-790`、`api/config.py` ChatRequest.packs）。

### 2.5 参考实现：AI 脚本生成工具（最新的"写工具"范式）

`njmind_form` 的两个脚本工具是当前"写工具"（产出代码/文本制品）的最新参考
实现，写同类工具优先照这套结构抄：

- `tools/generate_js_script.py`（字段权限 JS 脚本）与
  `tools/generate_filter_sql.py`（过滤条件 SQL）：`CompositeTool` 子类，
  `steps=["locate","generate","check"]` 三步管线；check 失败带原因重试
  （≤2 次），达上限仍失败则**诚实丢弃产物**（未通过校验就不谎称"已生成"）；
- 共享层 `tools/_script_common.py`：递归字段目录蒸馏（LLM 只见每字段一行
  的目录，不见全量 JSON）、`[script:js]`/`[script:sql]` 消息标记、
  SQL 系统列白名单。

另一个参考是 **njmind_bpm**（pack 专有上游端点的接入范式）：其 parse/render
端点不进通用 adapter（保持 `HttpAssetClient` 零领域知识），而是复用
`enhance_asset_client(asset_client, upstream)` 装配钩子只取 upstream 参数
注入 pack 专有 transport（`pack.py:35-43` + `service_locator.py`），
`main.py` 零改动。

## 三、manifest：插件向平台声明一切

`config.yaml` 是**领域差异的唯一载体**——前端和引擎读它，但不认识里面的业务词。

```yaml
artifact:
  type: form-config                  # 制品类型标识（应用时原样传给宿主）
  actions: [view_json, apply, rewind] # 配置卡片显示哪些动作按钮（见 4.1）
  identity:                           # diff 的数组对齐键（JSON path → 身份键）
    formFieldConfigVos: fieldTitleKey
  display:                            # 前端渲染辅助（全部可选）
    title: formName                   # 会话自动命名取哪个属性
    item_label: fieldTitleText        # diff 列表项显示名取哪个属性
    welcome_icon: form                # 欢迎页大图标（前端通用图标集名）
    data_labels: {applicant: 申请人, leaveType: 请假类型, ...}  # 数据卡 key→中文
    data_hidden: [status, approvalId] # 数据卡不展示的内部字段
    welcome_examples:                 # 欢迎页示例卡（点即填入输入框）
      - {title: 请假申请表, desc: 姓名、开始日期、事由,
         prompt: 创建一个请假表单，包含姓名、开始日期、事由, icon: form}
services:
  njmind-modeler: {}                  # 依赖的上游服务名（地址由宿主/env 提供）
```

**举例说明它为什么这样设计**：前端 `ChatPanel.vue` 是所有插件共用的通用组件，
它不会出现"请假类型"“表单”这类词。当请假插件上线，只需在自己的 config.yaml 写：

```yaml
display:
  welcome_examples:
    - {title: 请年假, desc: 3 天，本周五起, prompt: 帮我请 3 天年假，本周五开始, icon: form}
  data_labels: {applicant: 申请人, leaveDays: 天数}
```

欢迎页示例、数据卡标签**自动**换成请假的——前端零改动。这就是"组件保留机制、
内容住 pack"的含义。

`GET /api/meta/packs` 把所有 pack 的声明只读吐给前端（`api/meta.py`）。

### 3.1 依赖门控（可选：插件需要外部基础设施时）

插件要用 Neo4j/pgvector 这类外部设施时，在 manifest 里**声明依赖 + 探针**：

```yaml
dependencies:
  neo4j:
    required: true
    fields: [neo4j_uri, neo4j_user, neo4j_password]   # 配置来源 key
    probe: {module: domains.my_pack.probes, fn: neo4j} # 连通性探针
  pg_vector:                                            # 平台内置探针(实现下沉 SDK)
    required: false
    probe: {kind: pg_vector}
admin:
  settings: settings.schema.yaml   # 声明式设置页(连接信息可在管理端补配)
```

- 配置解析链：**设置页 > env > 默认**——部署后没配 env 也能在管理端补配
- 未配置/探针失败 → 插件中心显示"依赖未配置"，**不可启用**（fail-closed）；
  配好后点"重新检测"**热加载**，无需重启
- 探针自建短超时连接，不与运行时共享连接池；`pg_vector` 用平台内置
  `kind: pg_vector`（`sdk/vector_store.probe_pg_vector`，探 PG pgvector 扩展），
  领域专属设施才自写探针模块（参考 `knowledge_graph/probes.py` 的 neo4j）

### 3.2 声明式设置页（可选：插件有可调参数时）

`settings.schema.yaml` 描述分组表单，管理端自动渲染（读写走
`GET/PUT /api/admin/packs/{name}/settings`），**零前端代码**：

```yaml
# settings.schema.yaml
version: 1
groups:
  - key: connection          # 分组
    title: 存储连接
    fields:
      - key: neo4j_uri       # 字段 key(插件读配置用)
        type: string         # string | secret | int | float | bool | select
        label: Neo4j 地址
        env: NEO4J_URI       # 对应环境变量(设置页没存值时的回退来源)
        required: true
        placeholder: bolt://localhost:7687
        help: 图谱存储;本机 docker 可用 kg-neo4j 容器
```

配置解析优先级：**设置页保存值 > env > default**——部署后没配 env，
在管理端补配即可（配合依赖门控的"重新检测"热加载）。

### 3.3 管理页（可选：插件要自己的管理界面时）

```yaml
admin:
  page: knowledge_graph    # 前端注册表 key
  title: 知识图谱
```

管理端（`/ai-modeler/admin.html`）的插件 Tab 会为启用的插件动态挂一个自定义页
（前端 `packPages/registry.ts` 按 key 解析组件）。知识图谱插件用它做了
文档导入 / G6 图谱浏览 / 本体设置三个子页——**管理端不认识"知识图谱"，
它只认注册表里的 key**。

## 四、进阶插件形态：HTTP API + 后台任务 + SDK 存储

"请假"是最小插件形态（一个目录 + 工具）。知识图谱插件展示了**全能力形态**——
pack.py 四个钩子齐备：

```python
# domains/knowledge_graph/pack.py
def create_registry(app_state=None):     # ① 必须:工具注册(kb_search)
def create_api_router():                 # ② 可选:插件自有 HTTP API
def register_tasks(manager, app_state):  # ③ 可选:后台任务 handler
def unload():                            # ④ 可选:清理(释放连接/注销前缀)
```

**② 插件自有 HTTP API**：返回一个 `APIRouter`，平台统一挂到
`/api/packs/{pack_name}` 前缀（`services/pack_api_mount.py`），插件启停时
热挂卸。管理页/宿主系统直接调这些接口（如 `POST /api/packs/knowledge_graph/search`）。
管理端鉴权用 `sdk/pack_api.py` 的 `admin_required` 依赖。

**③ 后台任务**：长活（文档导入要分钟级 LLM 抽取）不能占请求线程。注册 handler 后
`mgr.submit("my.task", payload=..., queue_key=...)` 提交：

- **queue_key 串行**：同 key 任务 FIFO（如同库导入不并发写图）
- **协作式取消**：handler 周期检查 `handle.cancelled`
- **可观测**：`handle.set_progress(pct, msg)` 推进度、`handle.log(msg, **fields)`
  写请求级结构化日志（对齐 call_logs 粒度）；任务中心 SSE 实时刷新
- **断点续跑**：handler 自己落 checkpoint（done = 数据已落库），重跑跳过已完成块

任务可在**通用任务中心**统一观测（`api/tasks.py`，admin 鉴权，零任务类型
知识）：`GET /api/tasks` 分页列表、`GET /api/tasks/{id}` 详情、
`GET /api/tasks/{id}/logs` 日志回放（id 游标断线补齐）、
`POST /api/tasks/{id}/cancel` 取消、`GET /api/tasks/{id}/events` SSE 实时
事件流（snapshot/progress/log/status）——任何 pack 提交的任务都从这里看与停。

**④ SDK 存储设施**：图/向量/文档解析已下沉 `sdk/`，插件只写薄适配层
（参考 `knowledge_graph/stores.py`）：

```python
from sdk.scope_registry import register_prefix, new_scope_id

register_prefix("kg", owner="knowledge_graph")   # 前缀登记(撞名装配期 fail-fast)
graph = sdk_graph.get_graph_store(settings, prefix="kg_")   # 单例工厂
scope = new_scope_id()                            # scope_id 服务端签发,禁用户输入直传
```

两条隔离契约（前缀先登记后使用 + scope_id 服务端签发）+ 三个 SDK 调用 = 全套
命名空间隔离存储。完整契约与 NL2BI 接入示例见
`backend/src/domains/ARCHITECTURE.md`「SDK 存储设施」。

除知识图谱外，**chatbi**（智能问数：ask_data/switch_chart 工具 + 数据源管理
HTTP API + 元数据定时刷新后台任务 + 管理页）是另一个全能力 pack；**njmind_bpm**
（流程配置 AI）是**最简 pack 的新范本**——单一 `generate_process` 工具承担全部
生成/修改/重做（画布已有流程时按新描述整体重造回显覆盖）+ `bpm_chat` 兜底，
七步管线（fetch_guide → fetch_existing → fetch_form_catalog → parse_intents
→ fetch_templates → generate → render，机械修复 ≤4 轮/重生成 ≤3 轮）；其分支
字段确认门是 engine 结构化追问透传的首个消费方（question 为含 options 的 JSON
字符串 → 前端点选卡）。路由只覆写 `build_prompt` 不覆写 `route`——只有"重造
回显"一条路,无 create/update 分流歧义（`domains/njmind_bpm/pack.py`、
`router.py`）；**njmind_list**（列表页配置 AI）与 BPM 同走"单一工具整体
重造回显"路线——`generate_list` 承担全部生成/修改/重做 + `list_chat` 兜底,
六步管线（fetch_guide → fetch_existing → parse_intents → fetch_templates
→ generate → validate）,validate 前嵌 **SQL 过滤子管线**（三个 SQL 位的
占位一律重生成 + 机械校验,失败回退中性不过滤形态不阻断整单）;其 SQL
契约直接复用 njmind_form 的 `_sql_contract`（`check_sql_fragment`/
`xml_escape_sql`）——**跨 pack 复用契约层的首个案例**：契约住在被复用方
的 tools 层,复用方只 import 不复制规则（`domains/njmind_list/tools/
generate_list.py:35-38`）；**flow_studio**（流程编排）目录已预留、尚未实现。

## 五、交互模式（用户看到什么）

### 5.1 配置卡片的动作（manifest actions 驱动）

| 动作 | 显示条件 | 行为 |
|---|---|---|
| 查看 JSON | pack 声明 `view_json` | 全屏弹窗：**GitLab 风格 diff**（红删绿增、双侧行号、+N −M 统计），基线=画布/上一版；一键切换"完整"视图 |
| 切换到此版本 | pack 声明 `rewind` 且该版非当前生效版本 | 见 4.2（对话保留，版本卡互跳） |
| 应用 | pack 声明 `apply` **且** 嵌入模式 **且** 宿主 capabilities 含 apply | 见第五节 APPLY（三重判定：制品适不适合 × 场景对不对 × 宿主能不能） |
| 复制 JSON | 宿主无 apply 能力时 | 逃生口：内容永远能带走（独立于 actions 声明） |

未声明 `actions` 的插件回退最小集 `[view_json]`。

### 5.2 版本切换（git checkout 式：对话保留，只切数据）

版本即对话流本身——每个配置卡片就是一个版本锚点，没有独立的"版本库"页面。

点卡片上的「切换到此版本」（任何**非当前版本**的卡片都显示此按钮，包括最后
一张）→ 当前制品恢复为该版本 + diff 基线设为切换前版本（「查看 JSON」能看到
这次切换改了什么）+ 嵌入模式下自动渲染回画布。**对话记录始终保留**——想
"反悔用最新"就点最新那张卡的同一按钮，版本卡互为跳转锚点。切换后继续对话，
修改基于切换后的版本（嵌入走 GET_CONTEXT、独立走 context 传递）。

按钮按 pack 声明显示（`actions` 含 `rewind` 时）。

### 5.3 窗口形态（嵌入模式）

- 宿主页面右下角悬浮球，点击开窗（窗口右下贴底），**打开时悬浮球隐藏**，窗口内
  关闭后球回来；窗口保活（关=隐藏 iframe），重开继续上次会话；
- 窗口顶部右上角：**➕ 新对话**（清空当前对话回到欢迎页——嵌入布局无侧栏，
  这是唯一的重开入口；流式生成中禁用）与 **✕ 关闭**；
- 查看全屏 JSON 时，子应用发 `RESIZE(expanded)` 请宿主把窗口临时撑大到近全屏，
  关闭恢复——iframe 内弹窗最大就是 iframe 视口，不撑大看不清。

### 5.4 健康监控（宿主侧）

宿主页面加载时探测 `GET /ai-modeler/api/health`（走与 iframe 相同的代理链，
通过 = 代理与后端两层都活）——**仅健康时显示 AI 入口**（悬浮球与页面按钮同一
门控），服务未部署/挂掉时入口一致隐藏，用户不会遇到"点了没反应"。探测 3 秒
短超时，失败静默。后端同时提供根路径 `/health`（运维/K8s 探针惯例）与
`/api/health`（代理链别名）。

## 六、与宿主交互：嵌入契约协议

### 6.1 信封格式（所有消息的统一外壳）

```jsonc
{ "v": 1, "src": "host", "id": "r7", "type": "APPLY", "payload": { ... } }
//  v   协议版本
//  src 发送方身份：'host'（宿主）| 'child'（子应用）——双向校验，丢弃无 src 的消息
//  id  请求-响应关联（仅请求类消息）：响应回填同一个 id 于信封顶层
//     ⚠ 常见坑：id 放 payload 里子应用永远匹配不上 → 全部超时
```

### 6.2 八种消息

| # | 方向 | type | 性质 | 用途 |
|---|---|---|---|---|
| 1 | 子→宿 | `READY` | 通知 | 子应用加载完成，宿主此时才发 INIT（早发会丢） |
| 2 | 宿→子 | `INIT` | 指令 | 握手主入口：userId/headers(鉴权)/services(地址表)/artifact(当前制品)/revision/capabilities/packs(插件链路声明——原只控制前端展示如欢迎示例过滤,现**贯通到 chat 请求**：前端原样回传,后端一级路由只在子集内路由) |

| 3 | 子→宿 | `GET_CONTEXT` | 请求 | 每次发消息前拉宿主最新制品（AI 的修改基线） |
| 4 | 子→宿 | `APPLY` | 请求 | 把新制品交给宿主渲染（附 baseRevision 供漂移检测） |
| 5 | 宿→子 | `AUTH_UPDATE` | 通知 | token 刷新，鉴权头整体替换（与嵌入设计 §4.5.5 及 hostPort 实现一致——增量合并无法表达"删除某头"） |
| 6 | 子→宿 | `GET_AUTH` | 请求 | 主动查询最新鉴权 |
| 7 | 子→宿 | `CLOSE` | 通知 | 请求收起窗口（宿主只隐藏 iframe，会话保活） |
| 8 | 子→宿 | `RESIZE` | 通知 | 临时撑大/恢复窗口（`mode: expanded/normal`） |

### 6.3 一次完整对话的时序（举例）

```
宿主(designer)                子应用(iframe)              后端
    │ ←─ READY ────────────── │                           │    iframe 加载完成
    │ ── INIT ─────────────→ │                           │    headers/services/
    │    {userId, headers,    │                           │    capabilities:['context',
    │     services,artifact,  │                           │    'apply','auth'],
    │     revision,           │                           │    artifact=当前画布配置
    │     capabilities}       │                           │
    │                         │ ← 用户输入"把姓名改必填" ── │
    │ ←─ GET_CONTEXT(id:r1) ─ │                           │    发消息前拉最新基线
    │ ── GET_CONTEXT_RESULT ─→│                           │
    │    {artifact, revision} │ ── POST /chat(SSE) ─────→ │    增量管线(§七)
    │                         │ ←─ 实时 stage 事件 ─────── │    进度条逐节点推进
    │                         │ ←─ result(新配置) ──────── │
    │                         │   用户点「应用」            │
    │ ←─ APPLY(id:r2) ─────── │                           │
    │    {artifact, baseRevision:r1的revision, summary}    │
    │  [漂移检测：画布 hash ≠ baseRevision → 弹确认框]      │
    │  渲染到画布(不落库,isSaved=false)                     │
    │ ── APPLY_RESULT ──────→ │                           │
    │    {ok:true, artifact, revision}                     │
    │                         │ "已应用到画布，请手动保存"   │
```

### 6.4 能力协商与优雅降级

INIT 的 `capabilities` 决定子应用的功能开关，缺什么降级什么：

| 宿主 capabilities | 子应用行为 |
|---|---|
| 无 `apply` | 应用按钮消失，退化为「复制 JSON」（内容总能带走） |
| 无 `context` | 用会话内上一次配置继续（可能陈旧） |
| 只实现 READY/INIT/CLOSE | 最低形态：能对话、能生成、能复制（增量采纳的底线） |
| 不认识 `RESIZE` | 静默忽略，弹窗仍全屏占满 iframe 视口（fire-and-forget 设计） |

### 6.5 宿主接入的两种方式

**方式 A：自建适配器**（mind-designer 的做法，生产推荐）——宿主自己实现
消息处理。参照 `mind-designer/src/views/WidgetConfig/Header/useAIAssistant.ts`
（唯一适配文件，约 300 行）：挂 iframe（同源反代 `/ai-modeler`）、onMessage 分发
八种消息、`postToChild` 信封、序列化画布配置响应 GET_CONTEXT/APPLY。

**方式 B：SDK 浮窗**（`frontend/src/embed.ts`，快速集成/演示）——

```html
<script src="http://你的部署:13080/ai-modeler/embed.js"></script>
<script>
  const modeler = new LLMFormModeler({
    baseUrl: 'http://你的部署:13080/ai-modeler',
    userId: 'zhangsan',
    getArtifact: () => myDesignerConfig,          // 你的"画布"当前配置
    onConfigApply: (config) => renderToMyDesigner(config),  // 应用回调
  })
  modeler.open()
</script>
```

SDK 内部实现了完整契约（READY 握手/INIT 带全量 payload/GET_CONTEXT/APPLY/
GET_AUTH 响应/CLOSE/RESIZE），演示页 `public/embed-demo.html` 可直接跑。

### 6.6 上游服务地址（请求级解析，唯一来源：宿主 services 表）

插件在 manifest 声明它需要的**服务名**（如 `njmind-modeler`），地址由宿主
INIT 的 services 表按请求下发，直接采用；未下发则抛
`ServiceUnresolvableError`（fail-closed）。

配合 SDK 的 `preflight(state, ctx)` 钩子：引擎在 execute 前调用（流程链路的
标准环节），**每个插件自己写执行前提校验**——如 njmind_form 的工具校验上游
地址可解析，缺地址在进管线前就拦截，错误直达用户，不烧 LLM/上游调用。

换宿主/换环境，地址跟着宿主走，插件与后端零配置。每轮请求实际采用的地址
可在会话链路 `request_context` 打点中追溯。

## 七、增量修改协议（modify 为什么快）

modify 工具是两相式（Claude Code 编辑大文件同源思路）：

```
用户："把姓名改成必填"
  │
  ├─ 增量主路径（默认，实测 4s，旧全量路径 37s）
  │    build_catalog：配置 → 字段目录（~1KB，每字段一行含选项摘要）
  │    plan_ops：LLM 只输出指令集（几百字节）——
  │        {"ops":[{"op":"update_field","key":"xingming",
  │                 "patch":{"isRequiredField":1}}]}
  │    apply_ops：纯代码确定性合并（双锚定位/原子性/同类型克隆补全）
  │    restore_untouched：未提及字段从基线逐字节还原（改 A 绝不动 B）
  │    差分校验：AI 只为新增违规负责（存量违规不背锅）
  │
  └─ 全量兜底（LLM 主动 full_rewrite / 指令重试超限 / 输出不可解析时升格）
```

六种指令：`update_field` / `add_field` / `remove_field` / `update_form` /
`update_button` / `full_rewrite`。协议全部住在插件层（`_incremental_ops.py` +
`modify_ops.j2`），引擎零感知——下个插件可自带自己的指令集或继续全量。

**标识禁改（双层硬约束）**：`formCode`（表单编码）与已有字段的 `fieldTitleKey`
是数据库标识、与已存数据关联，禁止修改——改字段名只改 `fieldTitleText`。约束
在两层同时生效：prompt 写明（但 LLM 可能不听）+ **代码级保护**（增量层
`update_field` 静默剥离 patch 里的改名尝试并留痕；全量兜底路径产物强制回填
基线 `formCode`——真实事故：某单升格全量后 LLM 漏写 formCode，产物直接丢了
表单标识）。
校验还有一层**机械修复循环**（不烧 LLM）：「必填项缺失/值域不合法/未知字段」
三类确定性错误，值从「表内同类型字段 → 上游模板 → config 兜底表」三级抄写，
在本地循环修完——实测把"每单必挂一轮 35s 重试"变成首轮一次通过。

## 八、FAQ

**Q：AI 会把我的表单存库吗？**
不会。"AI 永不落库"是硬约束——所有工具的产物只到画布（渲染+isSaved=false），
保存只属于业务人员点保存按钮。

**Q：用户手动改了画布，AI 再应用会冲突吗？**
APPLY 带 baseRevision（基线指纹），宿主发现画布已漂移会弹确认框（覆盖/取消）。

**Q：切换版本后继续对话，基于哪个版本修改？**
基于切换后的版本（嵌入走 GET_CONTEXT 拉画布、独立模式前端传 context）。
对话记录始终完整保留，随时可再切回其他版本（包括最新）。

**Q：换个宿主系统要改子应用代码吗？**
不用。宿主实现八种消息（最少 READY/INIT/CLOSE 即可用），地址/鉴权/能力全部
握手协商。反向也一样：换插件，宿主零改动。

**Q：SSE 卡住/一直没响应？**
三道保障已内置：15s 心跳、响应头 `no-transform`（防代理 gzip 攒包——rsbuild
等 dev server 的 gzip 中间件会把 event-stream 攒到流结束才吐，这是真实踩过的坑）、
前端 60s 空闲看门狗明确报错。

**Q：我的插件需要 Neo4j/pgvector 这类外部依赖，怎么优雅接入？**
manifest 声明 `dependencies` + 探针（见 §3.1 依赖门控）——未配置 fail-closed 不可启用，
配好热加载。存储本体走 SDK 设施（见第四章），不要自己写连接管理。

**Q：长任务（导入/训练/批处理）怎么做？**
走后台任务框架（见第四章）：`register_tasks` 注册 handler + `queue_key` 串行 +
checkpoint 断点续跑。不要在工具 execute 里做分钟级长活——SSE 请求会被拖死。
失败自动续跑的边界要知道:致命错误(鉴权/欠费/配额)与**永久性错误**
（`sdk.pack_api.PermanentTaskError`,参数/校验类,重跑恒定失败——
如请求里引用了不存在的资源 id）都不会续跑;写这类校验时抛 PermanentTaskError,
否则配置错误会以 5 分钟一轮的节奏无限空转。

**Q：插件能有自己的管理界面吗？**
能。manifest `admin.page` 声明组件 key，前端注册表解析（见 §3.3 管理页）。
