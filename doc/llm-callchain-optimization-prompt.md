# LLM 调用链降频优化 · 通用提示词

> 用法：把本文件全文作为提示词发给另一个项目的 AI 助手。
> 该项目与本仓库架构同源（FastAPI + 图编排引擎 + 插件路由 + 管理端），
> 但以对方代码实际为准——先测量，后动手。

---

## 角色与目标

你是资深后端架构师。本系统一次用户请求会触发多次 LLM 调用（可能十几次），
全部串行，延迟和成本都高。你的任务：**在完全不降低回答正确性的前提下，
减少每次请求的 LLM 调用次数与用户等待时间**。禁止为了降次数牺牲答案质量。

## 第一步：先测量，建立基线（不动任何代码）

1. 找到对话入口路由，从入口完整追踪一次请求的全部 LLM 调用点。
  对每一处记录：stage/用途（意图路由？槽位提取？改写？标题？最终生成？）、
  代码位置、串行还是并行、温度参数。
2. 在本地栈发 3 条真实典型请求（每条业务链路各一），等它完成。
3. 用调用日志/trace 接口拉出每条请求的逐条调用明细（stage + 耗时），
  存为基线：总次数、总耗时、每步耗时。
4. 区分两类调用：**确定性小任务**（温度=0、prompt 模板固定、输出是短 JSON：
  路由/抽取/判定/改写/标题）与**大生成**（最终回答/结论/SQL——每链路一次）。

## 第二步：对照浪费模式清单逐项排查

以下是同架构项目实测存在的六种浪费，逐项核对本系统是否存在：

1. **会话标题每轮重生成**——标题是会话级产物，第 N 轮还在调 LLM 取标题就是纯浪费。
   修法：生成前查会话是否已有非空标题，有则跳过（读库失败 fail-open 回退旧行为）。
2. **单工具/少工具插件走 LLM 二级路由**——插件只有 2~3 个工具且 when 描述是
   关键词式时，用确定性规则路由（零 LLM）。⚠️ 红线：首查请求里出现图表词/
   产物词不得误路由到「修改/切换」类工具——路由规则必须双条件（切换动词+目标词），
   并写单测锁定「首查带产物词必须走主工具」。
3. **结果产出后的旁路任务阻塞主流程**——记忆提炼/统计上报这类「结果已生成后
   才做的事」丢后台线程（单 worker 串行即可），参数先快照防 state 突变，
   失败 fail-open 只记日志。
4. **由已知信息反推的 LLM 调用**——典型：检索 query 本来就是上游用槽位模板
   拼出来的字符串，下游又让 LLM 从这个字符串里「抽取实体」。直接用上游槽位
   确定性构造下游输入，省整次调用且精度更高。原始输入场景仍走 LLM 兜底。
5. **首屏可并行的小任务串行等**——与主链路无依赖的调用（如标题）提交后台
   并行跑，收尾节点限时合并（超时 2s 取不到就当没有，fail-open）。
6. **缓存一刀切禁用**——因为「混用途错层风险」整体关缓存是过度保守。

## 第三步：缓存只按 stage 白名单启用（正确性设计要点）

- **只缓存确定性小任务**：温度=0 且输出为短 JSON 的 stage（路由/抽取/判定/
  改写/标题/配置生成）。**最终回答、结论、SQL 生成永不缓存**——用户可见的
  答案必须每次现场生成。
- **缓存键 = 完整 prompt（逐条 role+content）+ 模型 + 温度 + max_tokens + 供应商
  端点**。任何一个字不同即不同键：配置表改了、schema 词汇表改了、会话背景变了，
  prompt 跟着变，自动不命中旧结果——不存在「配置改了还吐旧答案」。
- 进程内 LRU（~4096 条）+ TTL（~24h），重启即清；命中记 0ms 日志单独可查。
- **逃生门**：环境开关一键全关（默认开），关闭后行为与改造前完全一致。

## 第四步：验证（缺一不可）

1. **路由单测**：锁定误路由红线（首查带产物词→主工具；切换短语→切换工具；
   含元问题子串的长句→主工具；确定性路由永不调 LLM）。
2. **端到端质量回归脚本**：对运行中的本地栈发真实请求——
  S1 典型问：答案结论正确 + 新机制生效（对应 stage 从调用链消失）；
  S2 同题复访：缓存命中且**结论与首答一致**；
  S3 追问流：缺槽挂起→补槽→结论正确；
  S4 兜底路径：无结构化输入时 LLM 解析兜底仍在。
3. 全量测试套件绿。
4. 复测基线同题：给出改造前后「次数/耗时」对照表，数字必须来自真实日志。

## 交付物

① 基线表（改造前每链路次数/耗时）② 改动清单（每项附代码位置与原理一句话）
③ 改造后对照表 ④ 质量回归脚本与结果 ⑤ 路由红线单测。
预期量级参考（同架构实测）：典型链路首问 6→4 次真出站、关键路径 -25%等待；
同题复访只剩最终生成 1 次真出站。

## 红线回顾

- 只砍纯开销，不动回答质量；最终生成永不缓存。
- 每处优化 fail-open：守卫/缓存/后台线程失败时退化为旧行为，不阻塞主流程。
- 改完必须跑质量回归脚本对比答案，不许只看次数不看正确性。
