# 08 · 记忆与上下文

> 会话记忆的生产/存储/消费/遗忘全链，与多轮上下文管理。

## 1. 会话记忆体系（v0.23 引入，v0.24 Memory API）
> 🗺 对应链路图：[../图/ragflow-memory.html]（produce 视图）

**生产链**：
- 会话保存时异步投递 Redis 任务（memory_api_service.py:337 → memory_message_service.py:376）
- task_executor 消费 → LLM 抽取 **semantic/episodic/procedural 三类记忆**（:445,107）
- 抽取结果嵌入写入 message 检索索引（:214）——记忆本体不落 MySQL

**存储双轨**：
- Memory 表（db_models.py:1810 起）：memory_type 位掩码（1/2/4）、forgetting_policy、memory_size、storage_type（table|graph）、embd_id/llm_id 独立配置
- 本体进检索引擎与对话同引擎——记忆检索复用混合检索

**消费与遗忘**：
- 对话时按相似度召回记忆注入上下文
- 超 memory_size 按 **FIFO 淘汰**最旧记忆
- 前端 memories 页面可视化（web/src/pages/memories）

## 2. 多轮上下文管理
> 🗺 对应链路图：[../图/ragflow-memory.html]（store 视图）

- **full_question 多轮合成**（generator.py:256）：把多轮对话压成完整独立问句再检索——检索器永远拿到自包含问题；相对日期锚定（{{today}}/{{yesterday}} 注入）
- API4Conversation 消息 JSON 内嵌（含 reference/dsl/round/thumb_up）——会话即审计轨迹
- 画布侧：sys.conversation_turns 计数 + 每轮重置防脏值（canvas.py:539-549,576）

## 2.5 对话历史 token 窗口截断（终审补盲）
- `message_fit_in`（generator.py:69）：按 max_tokens×0.95 **逐条从旧到新裁剪**对话历史（dialog_service.py:840）——多轮上下文不是无限拼接，超窗先丢最旧消息
- 对 ChatBI 多轮（"查上月→再查上月环比"）直接相关：历史裁剪策略决定 prev_sql/prev_tables 继承多少

## 3. chunk 级反馈回路（v0.27）
> 🗺 对应链路图：[../图/ragflow-memory.html]（consume 视图）

- 消息 thumbup/thumbdown（chat_api.py:1025）→ ChunkFeedbackService.apply_feedback **按检索分加权**调整 chunk 的 pagerank_fea(0-100)（chunk_feedback_service.py:115-141）

## 对我们的启示

- **ChatBI 反馈断头的现成修法**：抄 chunk_feedback 模式——点赞/点踩按检索分加权微调表/字段置信度，开关默认关（蓝图 P2#14）
- 三类记忆+遗忘策略：我们 compact_focus 规模暂不需要，记录在案
- full_question 相对日期锚定：ChatBI"查上月销量"多轮场景直接可用（候选增强，未入蓝图编号）
- fewshot 回流加确认门：RAGFlow 的 thumbup 通道证明"人工信号→权重微调"闭环可行且轻量
