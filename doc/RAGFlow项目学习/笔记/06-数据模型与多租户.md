# 06 · 数据模型与多租户

> 37+ 张表的域划分、三个反直觉设计与权限模型。

## 1. 表全景（api/db/db_models.py，peewee ORM）

- **租户与模型**：Tenant / UserTenant / InvitationCode / TenantModel* 五件套（模型实例分组管理）/ LLMFactories / LLM / TenantLLM / TenantLangfuse
- **知识库域**：Knowledgebase / Document / File / File2Document / **FileCommit+Item（文件版本化）**
- **任务域**：Task / PipelineOperationLog / SyncLogs
- **对话域**：Dialog / Conversation / API4Conversation
- **编排域**：UserCanvas / **UserCanvasVersion** / CanvasTemplate / MCPServer
- **编译域**：CompilationTemplate + Group
- **连接域**：Connector / Connector2Kb
- **其他**：Search（独立搜索产品）/ Memory / ChatChannel / SystemSettings

## 2. 三个反直觉设计

1. **没有 Message 表也没有 Chunk 表**：消息+引用+错误全以 JSON 内嵌 API4Conversation（message/reference/dsl/thumb_up/round/errors）；chunk 只活在检索引擎。**元数据与检索数据彻底分离**——省 join、天然审计轨迹
2. **检索参数挂 Dialog 而非知识库**：similarity_threshold / vector_similarity_weight / top_n / **rerank_candidates_count** 都是 Dialog 字段——同一知识库可被不同检索策略的对话复用
3. **Memory 表自带遗忘策略**：memory_type 位掩码（semantic=1/episodic=2/procedural=4）、forgetting_policy、memory_size、storage_type（table|graph）

## 3. 权限模型

- 角色四档：OWNER/ADMIN/NORMAL/INVITE（api/db/__init__.py:23-27）；INVITE 受邀待确认，同意后升 NORMAL
- 三层防护：API 装饰器 login_required → service 层 accessible()（knowledgebase_service.py:569 等）→ SQL where tenant_id
- 知识库 TEAM 权限需 joined tenant 匹配（check_team_permission.py:33-37）
- 检索按 kb 所属 tenant_ids 限定（dialog_service.py:754-761）
- **已知弱点**：accessible 逻辑分散各 service，新端点漏加即越权；ADMIN 语义不完整

## 4. 认证链（api/apps/__init__.py:144-235）

- _load_user 依次尝试：session cookie（Redis 存储）→ Bearer 头 → itsdangerous JWT → APIToken 表 → BETA token
- 密码 werkzeug 哈希；登录口令 RSA 解密（私钥口令硬编码"Welcome"——安全教训）
- OAuth2/OIDC/GitHub 在 api/apps/auth/，state CSRF 校验

## 对我们的启示

- 消息+引用 JSON 内嵌会话：我们扩展 KG/ChatBI 对话功能时可顺手借鉴（会话即审计轨迹）
- 检索参数挂对话配置：同一库服务不同检索策略——KG pack 未来加"检索策略配置"时的挂载点参考
- 权限：我们宿主管权限（X-User-Id 透传），无需租户体系——但 service 层 accessible 的分散教训要记住（新端点统一走权限门）
