13 · 业务链路全景

第七轮：以业务链路视角串联全部技术维度——用户旅程、数据一生、问答全链、运维旅程与社区生态。每步链携带实现细节锚点（指向 01-12 笔记的具体节）。 本笔记是六轮研究的"串联层"：技术细节见各角度笔记，这里是它们发生的顺序。

1. 一次问答的完整旅程（带细节）

用户敲下问题到看到带引用的答案，全程约 3-15 秒，经历九站：

第 1 站：消息进入 - 前端 SSE 建流（chat API），消息追加进 API4Conversation 的 message JSON（06 笔记 §2：消息内嵌会话） - 画布场景则触发 Canvas._run_impl：每轮重置防脏值（05 笔记 §1，canvas.py:539-549）+ sys.* 注入（date/query/files/turns）

第 2 站：问句工程（检索之前） - full_question 多轮合成：已完整则原样返回；相对日期锚定（{{today}}/{{yesterday}} 注入，"上个月"→绝对日期）（11 笔记 §2） - keyword_extraction + cross_languages 跨语言增强（dialog_service.py:736-745） - 细节：这些 LLM 调用走 Redis 缓存——key=xxh64(模型+文本+用途标签+genconf)，同文本不同用途不同 key（02 笔记 §5.6）

第 3 站：多路检索 - 混合检索：向量 0.3/全文 0.7（search.py:602，注意网传方向相反） - 全文路：FulltextQueryer 构造 ES 查询——同义词展开（synonym.py 双层热更新：本地 JSON+Redis kevin_synonyms 每小时覆盖+WordNet 兜底，02 笔记 §5.5）、词权重 ^1.5、短语 ("词"~2) - KGSearch（可选）：query_rewrite 抽实体/类型 → P(E|Q)=pagerank×sim 排序 → n-hop 路径 → KG 结果 insert(0) 与普通结果并列 - Go 版三通道准入：BM25 精确→语义旁路（配额隔离）→metadata 预过滤，evidence 行豁免配额（02 笔记 §4）

第 4 站：融合与精排 - ES 侧取候选后本地重排（search.py:498-523）；空结果自动放宽复查（min_match=0.1、sim=0.17，:272-294） - rerank 可选（外部 API，启用时禁分页）——v0.18 教训：内置 rerank 性价比为负 - 融合公式细节：token 相似度含 bigram 0.6 权重（中文短查询词序不丢）；得分是查询覆盖率（文档答了问题的多少，非对称）（02 笔记 §5.2）

第 5 站：引用预埋 - chunk 携带 doc_id/kb_id/positions 坐标（:764-782）——回跳原文的物理基础 - reference 携 chunks+doc_aggs（dialog_service.py:855-894）

第 6 站：生成 - 检索资料以"ID/Title/Content"树形拼进 system prompt（generator.py:140-175）——无消毒（安全笔记 §6 的风险点，我们已有 defang） - 流式 SSE 输出，t0/t1/t2 三时刻被压测工具记录（09 笔记 §3）

第 7 站：引用插入（生成之后） - insert_citations 句级算法（02 笔记 §5.1 全参数）：代码块跳过、句界正则排表格行、阈值 0.63×0.8 递减兜底（保证尽量有引用）、每句≤4 chunk、全局去重、向量 0.9+token 0.1

第 8 站：前端渲染 - 主路径 reactStringReplace 替换为 HoverCard 胶囊+pdf-drawer 按 positions 定位；reference-utils 分组/轮播为死代码（02 笔记 §5.11） - XSS 防护：DOMPurify+rehype-sanitize，LaTeX 预处理后再消毒防 entity 绕过（10 笔记 §6）

第 9 站：反馈与沉淀 - thumbup/thumbdown → ChunkFeedbackService 按检索分加权调 chunk pagerank_fea(0-100)，开关默认关（08 笔记 §3） - 会话落定后异步投递记忆任务：LLM 抽 semantic/episodic/procedural 三类 → 嵌入入索引 → 超 memory_size FIFO 淘汰（08 笔记 §1） - Langfuse 埋点：仅单条 generation observation（比我们 call_logs 粗，09 笔记 §4）

2. 新用户端到端旅程（代码实证）

注册→登录：POST /api/v1/users（user_api.py:469）——无验证码无邀请码，邮箱正则即可；注册一次性建 User+Tenant（llm_id/embd_id/rerank_id 全空）+UserTenant(OWNER)+根目录 File；成功即自动登录。

模型配置（最大门槛）：v0.26 自动拉模型列表（GET /providers/<name>/models，provider_api.py:200）；保存默认模型必填 asr/embd/img2txt/llm 四 id（user_api.py:608）。不配置则 useWarnEmptyModel 弹不可关闭 Modal 强制跳转模型设置页——建库/聊天全被阻断，无内置兜底模型。

建库与上传：建库表单 embedding 预填租户默认+12 种切块模板下拉；POST /datasets 时 embd_id 为空即失败（dataset_api_service.py:132-137）；上传文件名≤128 字节，文档初始 run="0"（UNSTART），勾选 parseOnCreation 自动触发解析。

解析等待：Progress 进度条+progress_msg 滚动日志（前端轮询，无推送）；状态机 UNSTART/RUNNING/DONE/FAIL/CANCEL；FAIL 有 ReparseDialog 重试入口（失败图标即 reparse）。

首次问答：chat-settings 选库+llm+参数（默认 top_n=6、similarity 0.1）；发消息走 SSE 流（chunk 合并+reference 保留）；失败仅 notification.error+文本暂存，无诊断指引。

进阶入口：检索测试（dataset/testing → /retrieval）、Agent 画布（/agents/chat/completions）、搜索页、团队邀请（异步邮件）。

卡点/流失风险：①配置门槛最致命（新租户零模型必须先拿 API key）②等待焦虑（大文档解析无全局任务视图）③失败有路但浅（上传部分失败返回 500 混合消息；聊天失败无诊断）。

对我们：njmind 场景宿主预配模型（无此门槛）；但"解析等待期无全局任务视图"值得对照我们任务中心（我们 SSE 推送+任务中心已有，这是我们的优势项）。

3. 文档数据全生命周期（六态，代码实证）

诞生：POST /datasets/{id}/documents → MinIO put + Document 行（parser_config 继承 KB、content_hash=xxh128(blob)（file_service.py:656-673）、run=UNSTART/progress=0）。

解析态：parse API 先清旧（DONE 则 clear_chunk_num+删 Task+删旧 chunk，document_api.py:1627-1644）→ queue_tasks（PDF 按页拆 Task+digest 去重+复用旧 chunk，task_service.py:553-559）→ executor 领取 → DeepDoc→切块→嵌入 prog=0.82→索引 0.82→1.0；chunk_num/token_num 累加；progress_msg 3000 截断。DONE/FAIL 由 _sync_progress 聚合 Task 得出（document_service.py:1090-1162）。

编译态：手动 run_index（Task 挂 fake_doc_id，文档保持 DONE——begin2parse(keep_progress=True)）；doc 级 RAPTOR 在切块尾部按 use_raptor 自动触发（:1300-1342；03 笔记 §6：v0.27 已收编编译体系、UI 移除旧开关，此为旧口径）；RAPTOR checkpoint 跳过已有摘要并清 stale。

服务态：检索硬过滤 available_int=1；文档禁用批量刷（排除 compile_kwd 编译产物）；chunk 人工编辑→重分词+重嵌 q_vec（chunk_api.py:1309-1319）；编译产物不可手删（rm_chunk 用 must_not exists compile_kwd，:1203-1215）。

更新态：连接器 fingerprint 变化→同 doc_id 覆盖 MinIO+更新 hash→仅 hash 变化才重解析；图谱/RAPTOR 不自动重建需手动重跑（有 in-progress 任务则拒绝，dataset_api_service.py:615-616）。

死亡：remove_document 完整链（document_service.py:463-572）：Redis cancel→Task 行→chunk 图片→缩略图→dataset_nav→ES chunk→wiki 产物引用计数→metadata→图谱从 source_id 移除该 doc、无 source_id 者删除→Document 行+MinIO 对象。

状态机死角（对我们最有价值的部分）： - 永久 RUNNING：Redis 消息丢失而 Task 行残留 → 文档永久 RUNNING，无后台清扫器——我们 KG 有"启动收敛僵死 importing"（tasks.py:73-97），RAGFlow 反而没有，这是我们领先项 - CANCEL 屏蔽：取消后所有 progress 更新被 where run!=CANCEL 屏蔽，文档停 CANCEL 直至手动重跑 - 删不净角落：ES 删除失败仅 log→孤儿 chunk；图谱清理失败仅 warning→残留；f2d 行缺失时 MinIO 对象泄漏；dataset 级 RAPTOR 摘要（fake_doc）不随单文档删除

4. 运维旅程

  • 部署门槛：CPU≥4 核/RAM≥16GB/盘≥50GB；slim 镜像 1GB（v0.22 起弃 9GB full）；vm.max_map_count≥262144（ES 需要，Infinity 不需要）
  • 监控：任务心跳（pending/lag/done/failed）+ stats API（PV/UV/token）+ Jaeger 可选（默认关）
  • 故障手册（FAQ 口径）：任务队列卡死手清 Redis；RAM 不足解析被杀调 MEM_LIMIT；两度内存泄漏史（v0.19.1/v0.20.3）
  • 升级：切检索引擎=清库无迁移（down -v）；备份迁移有官方脚本（docs/administrator/migration/）

5. 社区生态与热度（2026-10 视角）

  • 热度：约 9.1 万 Star / 1.08 万 Fork / 463 贡献者；轨迹 2024-04 开源 → 2025-02 3.2万 → 2026-05 8万 → 2026-09 破 9 万；Issue 平均处理 33.6 天（十几人团队扛 9 万 Star）
  • 开发方：上海 InfiniFlow（英飞流，2023-08 成立，约十几人，同时维护 Infinity 数据库）；融资天使+两轮 Pre-A（创新工场/北极光）；用户海外:国内 ≈ 4:6；阿里云/腾讯云市场上架
  • Issue 热点 TOP（与 release notes 考古互证）：①解析慢/卡住/失败第一（20 页 PDF 12 核约 120 秒；GraphRAG 卡 80-90%）②资源门槛高（官方建议 ≥32GB，社区靠扩 swap 续命）③高并发会话冲突/内存泄漏 ④部署/模型下载报错
  • 生态定位：Dify 是"应用编排操作系统"（141k），RAGFlow 是"专注 RAG 的精密仪器"（9 万+）——常见组合"RAGFlow 检索层 + Dify 编排层"；迁移叙事：因解析深度从 Dify/AnythingLLM 迁入，因协作/权限弱迁出到 WeKnora
  • 商业化：Apache-2.0 无功能闭源；cloud.ragflow.io 定价未公开（SaaS→私有化/BYOC 三步走）；阿里云"RAGFlow 知识库"1.73 元/小时+增强解析 0.02-0.25 元/页——TiDB 式开源 ToB 路径
  • 差异化机会（对我们）：社区最痛四点=解析慢且重/资源门槛高/Issue 响应慢/协作弱。我们双插件若做到"解析快、轻量可跑、断点可恢复"，正打在 RAGFlow 最痛且 Go 重写 1.0 尚未完全解决的解析断层上——njmind 场景（Word/表格为主、无需 OCR 重管线）天然轻量，这是我们的差异化空间
