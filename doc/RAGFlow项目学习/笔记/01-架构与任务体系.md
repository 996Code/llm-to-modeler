# 01 · 架构与任务体系

> RAGFlow v0.27.2 的进程拓扑、任务执行、部署形态与"解析/编译/编排统一内核"设计。
> 配图：`../图/ragflow-system.html`（组件架构）、`../图/ragflow-doc-ingestion.html`（导入工作流）

## 1. 进程拓扑：慢工厂 + 快商店
> 🗺 对应链路图：[../图/ragflow-system.html]（request-path 视图）

RAGFlow 把系统切成两个节奏完全不同的部分：

- **Task Executor（慢工厂）**：解析、切块、建图、编译全是重活。Redis Streams 消费组把任务派给 N 个可水平扩的执行器（`docker/entrypoint.sh --workers=N`）。执行器自带 **worker 自杀式回收**：每完成 MAX_TASKS_PER_WORKER 个任务就退出重启——ONNX 推理库内存池只增不减，重启是最可靠的回收（task_executor.py:185-198 注释明言）。
- **API Server（快商店）**：Flask/Quart :9380，只做元数据、检索编排、对话生成，不碰重活。
- 可选进程：MCP Server（:9382）、Admin Server、data_sync 同步进程、沙箱执行器（entrypoint.sh 选项）。

**存储四件套**：MySQL 元数据（37+ 表）、MinIO 文档原件、Redis 队列/缓存/锁、检索引擎可插拔（ES/Infinity/OpenSearch/OceanBase+SeekDB/GaussDB/SereneDB 七选一，settings.py:398-424）。Jaeger/OTel 可选 profile。

## 2. 任务执行器内部
> 🗺 对应链路图：[../图/ragflow-system.html]（ingestion-path 视图）

- **领任务**：collect() 先恢复同名 consumer 的 unacked 迭代器，再领新消息；取消任务直接 ack 丢弃（task_executor.py:247-297）
- **任务分发表**：TASK_TYPE_TO_PIPELINE_TASK_TYPE 13+ 类——dataflow/raptor/graphrag/mindmap/memory/wiki/skill/structure_graph/structure_mindmap/timeline/session_graph/session_essence/structure（:131-145）
- **KB 级 fan-out**：知识编译类任务用假 doc_id 哨兵 + doc_ids 列表（:149-161）——图谱不是特权公民，只是十几种"把文档编译成知识形态"任务之一
- **切块模板工厂**：ParserType → 14 个切块模块（naive/qa/laws/paper/manual/resume/table/picture/audio/email/kg/tag…，:120-129）
- **进度上报**：set_progress 单调更新 progress/progress_msg 写回 MySQL（:229-244）
- **心跳**：report_status 上报 pending/lag/done/failed/current（:1870-1948）

## 3. 部署形态

- compose-base 服务：mysql/minio/redis/infinity/serenedb/oceanbase/seekdb/sandbox-executor-manager/jaeger/nats（v0.27.2 已含 Go 化过渡件）

## 5. rag/flow 数据流 DSL：三合一内核

`Pipeline(Graph)` 直接继承画布引擎（rag/flow/pipeline.py:28）；`ProcessBase` 继承 agent 的 `ComponentBase`（base.py:33）——**解析、编译、编排共用一个执行内核**，组件族 chunker/compiler/extractor/parser/tokenizer。dataflow 任务驱动（task_executor.py:797 run_dataflow）。

## 对我们的启示

| RAGFlow 设计 | 我们对应 | 判定 |
|---|---|---|
| Redis Streams + 消费组 + unacked | 线程池+queue_key+续跑（单进程） | 单实例契约是明示决策，等真实需求再扩（PG SKIP LOCKED 路线） |
| worker 自杀式回收 | 不需要（无本地 ONNX 长驻） | 记住手法即可 |
| 假 doc_id fan-out | pack 任务框架等价 | 已有 |
| Prompt 三层加载 | j2 外部模板 | 可加"管理页热改 prompt"（产品化方向） |
| 三合一内核 | 不效仿 | 无画布生态，收益不抵复杂度 |

## 6. 基础设施细节考古（第六轮）

- **KB 级分布式锁**（redis_conn.py:537-565）：key=graphrag_task_{kb_id}，TTL 1200s 无续期；acquire 先 Lua 原子删同值旧锁（幂等重入）再抢；release 用 delete_if_equal（值不匹配不删，防误删他人锁）；外层循环重试总超时 600s
- **progress_msg 截断**（task_service.py:132-145）：上限 3000 字符（env 可覆盖）；超限从头丢弃整行直到剩余 ≤3000——按字符截、保行边界、**留尾部最新日志**
- **并发闸门**（task_executor_limiter.py）：MAX_CONCURRENT_TASKS=5/chunk=1/minio=10/kg=2；实现为 LoopLocalSemaphore（WeakKeyDictionary 按事件循环各建信号量）；超限纯排队不拒绝——task_limiter 在取任务前 acquire，**占满即停止消费新任务（背压）**
